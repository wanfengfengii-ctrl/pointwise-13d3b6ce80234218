# 青榆小剧场字幕领播服务

文字编辑员把舞台监督提供的分段剧本定稿。场务将定稿绑定到登记屏开演，领播员按节目口令预取、点亮并处理勘误。场务收台后按实际点亮顺序复盘。

## 运行

使用 Python 3.11 标准库。从项目根目录运行以下命令。

```sh
python3 -B -m control.runtime serve --data-dir ./data --port 8765
python3 -B -m control.runtime demo
python3 -B check_project.py
python3 -B -m unittest discover -s tests -t .
```

`serve` 默认绑定本机 `127.0.0.1`，登记屏 P1 为六列。可用 `--screens` 指定 JSON 配置，例如 `{"screens":[{"screen":"P1","width":6}]}`。初始化只补缺失屏号。领播库 `control.sqlite3` 和屏端库 `display.sqlite3` 位于数据目录并分别提交。demo 在自己的临时目录用实际 HTTP 运行，样例输入在 `examples/`。`check_project.py` 由运行平台提供。

## HTTP

POST 接收 JSON 对象，GET 通过查询字符串传参。段号从 1 起。

| 方法 | 路径 | 输入 | 结果 |
| --- | --- | --- | --- |
| POST | `/publish` | `width`、`cues`，每条含 `cue`、`order`、`segments` | 201，稿号 `revision`、行宽及含正文和显示行的有序条段 |
| POST | `/open` | `show`、`screen`、`revision` | 200，场次的屏、初始稿和 `live` 阶段 |
| GET | `/preview` | `show`、`screen`、`cue`，可选 `segment` | 200，候选稿及一段或整条的排版行 |
| POST | `/advance` | `show`、`screen`、`cue`、`segment` | 200，已有实显的精确身份、稿号、序号和行，或 202 `pending` |
| POST | `/correct` | `show`、`screen`、`revision`、`request` | 200 `confirmed`，或 202 `pending` |
| GET | `/correction_status` | `show`、`request` | 同一勘误的结果，未查实返回 202 |
| POST | `/close` | `show` | 200，场次进入 `closed` |
| GET | `/history` | `show`、`screen` | 200，`events` 按实际点亮序返回条、段、稿号和序号 |

请求错误返回含 `error` 和 `message` 的 JSON。400 表示非法输入或不兼容稿，404 表示未知资源或不匹配的场屏，409 表示场次阶段、请求身份或播放顺序冲突。已结束场次仍可查询历史和原勘误结果。查询勘误只核实已提交的结果。需要重送尚未落实的勘误时，使用原请求号和原参数再次提交。

字幕条号唯一，`order` 为严格递增的正整数，每条有一至两段。定稿使用编辑员选定的正整数列宽。东亚宽度 W/F 占两列，其他基字符占一列，附着的组合标记占零列。按空白分词，词间加一个空格，超宽词按字符单元硬断。段内换行随定稿保存，预取与点亮都使用这些行。勘误可改正文和显示行，保持条号、条序与分段数。

预取只返回候选。不确定期间，尚未开条的首段等待核实，已开条的尾段按开条稿继续。屏端实际点亮时才取得实显序号。迟到的旧指令不能开条，迟到或重复的实显回报不会改写历史。样例先用 R1 点亮 C17 首段，再换 R2，C17 尾段用 R1，C18 首段用 R2。

## 本次新增的自动续段

开场请求可加 `"auto_tail":{"cue":"C17","delay_ms":5000}`。每场至多为初始稿中的一个双段条设定间隔，`delay_ms` 是正整数毫秒，布尔值无效。非法配置返回 400，场次仍可正常开场。首次开场省略该字段即沿用人工领播。重投开场时省略该字段或传相同配置均沿用原配置，试图为已开场的场次增设规则或更改配置返回 409。`/open` 的响应格式照旧。

首段实际点亮时开始计时，预取和请求受理均不启动计时。到期时刻是首亮时刻加上间隔。到期前保持原画面，只要两端可通信，首次可执行的到期轮询就须推进尾段，即使人工首段请求仍待核或服务已经重开。保持两端各自的提交边界。领播员可随时按原 `/advance` 口令手动续段，仍按已有播放顺序。自动和人工点亮的尾段均用首段实际使用的稿。历史仍只记录实际点亮，尾段最多实显一次。

`POST /auto_tail/cancel` 收 `show`、`screen`、`cue`、`request`，`request` 沿用原请求号的字符串规则。领播持久受理后，可用同号同参续办或查回原结局。取消请求号在同场的取消操作中唯一，同号异参返回 409。响应含上述身份和 `status`。屏端结局待核时返回 202 `pending`，查实时返回 200。取消先在屏端生效时，结局是 `cancelled`，已派出但未实际点亮的自动动作失效，人工仍可续段。尾段先亮时，结局为 `manual` 或 `auto`，并返回该次实显的 `sequence`。收台后新取消请求返回 409，已受理的请求仍可续办或复领。如果收台先于两种可能的结局，已受理请求的结局为 `closed`。每个请求的原结局永久保持，包括取消后再有人工实显的情形。

`GET /auto_tail` 按 `show`、`screen`、`cue` 查询，返回 200，含这三项身份和 `status`。`waiting` 表示尚无首亮，`armed` 表示已从首亮取得截止时点且自动资格仍有效，同时返回整数 `due_ms`。已实显时读 `manual` 或 `auto`，并返回原 `sequence`。尾段未亮且已取消时读 `cancelled`。收台已使未决的机会结束时读 `closed`。已取得的取消或实显结局可在收台后查询。没有相应配置或绑定的查询和新取消请求返回 404。收台后，迟到的自动动作不得新增实显。

## 续段演练

用 `examples/` 中的两稿开演，在 C17 实亮首段后隐藏回报，受控时钟从 10000 毫秒推进到 14999、15000，核对前一轮只亮首段，后一轮恰好补亮一次尾段。保留原回归，补充可重复的 HTTP 核验，覆盖到期前后、在途自动动作与取消、失答重开后的原号复领、先实际点亮的结果、换稿和收台。业务断言失败时以非零状态退出。

正常服务启动后自动轮询，使用以毫秒表示的时钟。演练可用 `build_runtime(..., clock_ms=...)` 注入一个返回整数毫秒的时钟，再以 `runtime.poll_auto_tail()` 显式驱动一轮。`rehearsal.py` 提供 `ManualClock`、`poll_at` 和通用 `Delivery` 夹具，也可用等效的受控消息手段暂停自动动作及隐藏取消结果。`python3 -B -m rehearsal` 验证原人工亮屏链路上的夹具行为。

`.pointwise-runtime.json` 已接通服务启动及本机 `/health` 就绪探针。清单使用版本 1、`api` 类型和参数数组，`setup` 是准备命令列表。交付时让 `verify` 核对原行为及上述联合轨迹，让 `demo` 用实际请求展示自动续段或取消结局。
